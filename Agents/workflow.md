# Workspace Workflow

이 문서는 `D:\VSCODE-WorkSpace`에서 수행하는 변경·명령 실행 작업의 공통 절차를 정의합니다. 루트 및 프로젝트별 `AGENTS.md`의 범위·기술 규칙과 함께 적용합니다.

## 1. 작업 분류

- 검토, 설명, 진단, 상태 보고는 Read-Only입니다.
- 사용자가 변경, 생성, 설치 또는 실행을 요청한 경우에만 해당 범위의 상태를 변경합니다.
- 요청과 무관한 문제는 임의로 수정하지 않고 별도로 보고합니다.

## 2. 범위와 종료 조건

작업 시작 전에 현재 요청의 범위를 다음 기준으로 고정합니다.

- **Goal**: 이번 작업이 직접 달성해야 하는 결과
- **Success Criteria**: 완료 여부를 판정할 수 있는 최소 검증 조건
- **Non-Goals**: 사용자가 요구하지 않았거나 이번 작업에서 다루지 않을 영역
- **Stop Condition**: Success Criteria가 충족되면 추가 개선 없이 작업을 종료한다는 조건

작업 중 새 문제나 개선 가능성을 발견하면 다음 순서로 판정합니다.

```text
발견 사항
→ 현재 Success Criteria 충족에 필수적인가?
   ├─ Yes → 현재 범위에서 해결
   └─ No  → 수정하지 않고 후속 사항으로 기록
```

- 발견된 위험, 개선점, 기술 부채는 자동으로 현재 요구사항이 되지 않습니다.
- 추가 안정성, 일반화, 추상화, 자동화, 성능 개선은 현재 Success Criteria에 필요하지 않으면 수행하지 않습니다.
- 새로운 dependency, service, container, daemon, framework, abstraction layer, system-wide setting 변경은 현재 요구사항에 필수적일 때만 도입합니다.
- 사용자가 명시적으로 요구하지 않은 production hardening은 별도 작업으로 분리합니다.

## 3. 실행 전 보고와 확인

작업 전에 다음 항목을 짧게 보고하거나 확인합니다.

- 목적과 요청 범위
- Success Criteria와 Stop Condition
- 필요한 경우 명확한 Non-Goals
- working directory와 정확한 대상 경로
- 관련 버전과 설정 적용 범위
- 실행할 명령 또는 작업
- 예상 영향과 산출물 위치
- 검증 방법

예시 명령과 경로는 예시라고 표시하며 실제 환경의 값으로 추측해 사용하지 않습니다.

## 4. 작업 모듈

관련 변경을 가능한 한 독립적인 작업 모듈로 나누고 다음 순서로 진행합니다.

```text
범위 확인 → 최소 구현 → 저장 → Success Criteria 검증 → 충족 시 종료 → 결과 기록
```

- 하나의 모듈 구현을 마친 뒤 저장하고 이어서 해당 모듈을 검증합니다.
- 이전 모듈의 검증 결과를 확인한 뒤 다음 모듈로 진행합니다.
- 검증에 실패한 경우에만 현재 Success Criteria를 만족시키는 범위에서 디버그·수정합니다.
- 파일 편집 도구가 즉시 저장하는 환경에서는 관련 변경을 하나의 일관된 편집 단위로 적용한 뒤 곧바로 검증합니다.
- 새 구조와 자동화는 현재 요구사항을 만족하는 최소 단위로 시작하고, 반복되는 실제 필요가 확인될 때 별도 작업으로 확장합니다.
- Success Criteria가 모두 충족되면 남은 비차단 개선점이 있어도 현재 구현을 종료합니다.

### 검토자 규칙

검토 또는 Reviewer 역할에서는 발견 사항을 다음과 같이 분류합니다.

- **BLOCKER**: 현재 Success Criteria를 충족하지 못하게 하는 문제
- **NON-BLOCKING**: 문제가 있으나 현재 Success Criteria에는 영향이 없는 사항
- **FUTURE**: 향후 확장, hardening, 일반화 시 고려할 사항

재작업 또는 `REVISE`는 **BLOCKER가 있을 때만** 요구합니다. `NON-BLOCKING` 또는 `FUTURE` 항목만 존재하면 현재 작업은 완료로 판정하고 해당 사항은 후속 보고에 남깁니다.

## 5. 명령과 승인

- 일반적인 Read-Only 확인, 빌드, 테스트와 요청 범위 내의 되돌릴 수 있는 명령은 별도 승인 없이 실행합니다.
- Critical한 영향이 예상되거나 되돌리기 어려운 작업은 실행 전에 승인을 받습니다.
- 승인 요청에는 `Why:`, 정확한 대상, 예상 영향, 복구 방법을 포함합니다.
- Critical 예시는 복구하기 어려운 삭제·덮어쓰기, 대규모 이동, 시스템 전역 설정 변경, 외부 서비스 쓰기·전송, 인증정보 취급입니다.

## 6. Critical 삭제·덮어쓰기 백업

### 적용 조건

- 기존 파일이나 폴더를 Critical하게 삭제하거나 복구하기 어렵게 덮어쓰기 전에 적용합니다.
- 재생성 가능한 빌드 산출물과 캐시는 기본 백업 대상에서 제외합니다.
- `.backups`, `.git`, `Binaries`, `Intermediate`, `Saved`, `DerivedDataCache`, `node_modules`는 재귀 백업 대상에서 제외합니다.

### 프로젝트 루트 판정

- UE 프로젝트는 대상 `.uproject`가 있는 폴더를 사용합니다.
- Git 프로젝트는 대상에서 가장 가까운 `.git` 상위 폴더를 사용합니다.
- 그 외에는 `package.json`, `pyproject.toml` 등 명확한 프로젝트 표식이 있는 가장 가까운 폴더를 사용합니다.
- 프로젝트 루트를 확정할 수 없으면 작업을 중단하고 사용자에게 확인합니다.

### 백업 구조

```text
<ProjectRoot>/.backups/
└─ YYYYMMDD-HHmmss-<task>/
   ├─ manifest.md
   └─ <원본의 프로젝트 상대 경로>
```

`manifest.md`에는 생성 시각, `Why:`, 원본 절대·상대 경로, 예정 작업, 크기·hash 또는 파일 수, 복원 위치와 방법을 기록합니다. `.backups`의 내용은 버전 관리에서 제외합니다.

### 실행 순서

```text
대상·영향 확인
→ 백업 위치와 복구 방법 보고
→ 사용자 승인
→ .backups에 복사
→ 백업 크기·hash 또는 파일 수 검증
→ 보존 개수 정리
→ 원래의 삭제·덮어쓰기
→ 결과와 복원 위치 보고
```

- 백업 생성 또는 검증에 실패하면 원래의 Critical 작업을 실행하지 않습니다.
- symlink 또는 Windows reparse point는 자동으로 따라가지 않고 중단하여 확인합니다.
- 예상 백업이 `1 GiB` 이상이거나 파일이 `10,000개` 이상이면 규모를 다시 보고하고 추가 확인을 받습니다.

### 보존 정책

- 현재 작업 파일은 백업 개수에 포함하지 않습니다.
- 프로젝트별 백업 스냅샷은 최신 2개만 유지합니다. 결과적으로 `현재 상태 + 직전 백업 + 그 이전 백업`까지 복구할 수 있습니다.
- 새 백업을 완전히 생성하고 검증한 뒤, 최신 2개를 초과하는 가장 오래된 스냅샷을 삭제합니다.
- `.backups` 내부의 보존 정책 정리는 재귀 백업 및 추가 승인 대상에서 제외합니다. 삭제한 스냅샷은 완료 보고에 기록합니다.
- 보존 개수 정리에 실패하면 원래의 Critical 작업을 실행하지 않고 원인을 보고합니다.

## 7. 실패와 재시도

- 실패한 명령을 원인 확인 없이 같은 방식으로 반복하지 않습니다.
- 오류, 종료 코드, 부분 변경과 산출물을 먼저 확인합니다.
- 원인과 영향을 보고하고 현재 Success Criteria에 필요한 범위에서 수정된 재시도 방법으로 진행합니다.
- 실패 원인이 현재 Success Criteria와 무관한 경우 작업 범위를 확장하지 않고 후속 사항으로 기록합니다.
- 별도 로그 파일은 작업상 필요하거나 사용자가 요구할 때만 생성합니다.

## 8. 완료 보고

- 성공 또는 실패 상태
- 실제 변경·생성·삭제된 항목
- Success Criteria와 검증 결과
- **BLOCKER**: 미해결 시 현재 작업이 완료되지 않는 문제
- **NON-BLOCKING**: 현재 결과에는 영향이 없지만 확인된 문제
- **FUTURE**: 향후 확장 또는 hardening 시 고려할 사항
- 필요한 로그와 백업 위치
- 사용자가 수행해야 할 다음 행동이 있는 경우에만 해당 행동

Success Criteria가 충족되고 BLOCKER가 없으면 현재 작업을 완료로 판정합니다. NON-BLOCKING 또는 FUTURE 항목은 완료를 막지 않습니다.
